Why it exists

Mappings often become critical project logic while living in files that cannot explain whether they are complete, valid, governed, or still aligned with the interface they serve.

01

Make intent explicit

Fields, transforms, conditions, and target paths live in a versioned contract instead of scattered interpretation.

02

Measure completeness

Required-target coverage and traceability make gaps visible before migration or integration testing.

03

Derive, don't duplicate

Generate governance evidence and adjacent contracts from the same reviewed source.

From mapping to proof

The useful unit is the chain from declared mapping intent to reproducible evidence a reviewer can inspect.

A small operating loop

map-code validate examples/customer-master.yaml
map-code score examples/customer-master.yaml --format json
map-code lineage examples/customer-master.yaml \
  --format mermaid --output lineage.mmd
map-code bundle examples/customer-master.yaml \
  --output release-bundle.json

What you get

A validated contract, quality and coverage signals, traceable lineage, and a portable evidence bundle. Explicit projections can also connect the contract to supported adjacent tools.

Not an ETL platform. The project governs transformation intent and derived artifacts; it does not replace your runtime or data movement layer.

Where it connects

Mapping is deliberately narrow. Its value grows when the reviewed artifact is referenced from an interface or reused by reconciliation without becoming a second source of truth.

Interface as Code →Bind the canonical mapping through the typed mapping.ref handoff.Reconciliation as Code →Generate a starting control or reuse a pinned lookup mapping directly.Process as Code →Reference mapping intent for traceability without evaluating it in the process model.
Agent entry point

Bounded enough for agents.

An agent should first read the manifest, validate the contract, then use deterministic CLI operations. Generation is explicit; evidence remains reviewable by a person.
